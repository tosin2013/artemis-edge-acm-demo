= Module 6: Store-and-Forward Resilience

== Objectives

* Simulate a network partition **on the NY SNO** (not between two pods on the hub)
* Produce to the SNO AMQPS Route while federation egress is blocked
* Observe store-and-forward when the ACM partition policy is disabled again

`{user}` cannot apply a NetworkPolicy on the SNO. The partition is an ACM policy in `edge-broker-policies` that a cluster-admin enables. Students still produce and consume from the hub.

[NOTE]
.Real WAN disconnection vs. lab simulation
====
This module simulates a partition using a NetworkPolicy that blocks pod-level egress. In a real deployment, a WAN failure is broader — the entire SNO loses connectivity to the hub cluster.

*What happens during real WAN loss:*

* The *klusterlet agent* on the SNO enters a degraded condition but does *not* remove existing resources. Workloads already deployed — including the AMQ Broker — continue running autonomously.
* *ACM policies already applied* remain enforced locally. The policy controller on the managed cluster continues to reconcile them. New policy changes from the hub will not propagate until connectivity restores.
* The *AMQ Broker* continues accepting local producer connections and queuing messages in the Artemis journal. Federation auto-reconnects when WAN restores (`reconnectAttempts=-1` in the broker properties).
* *Policy compliance status* on the hub goes stale — the hub shows the cluster as offline. This is expected behavior, not a failure.

In short: losing hub connectivity does not break local operations. The SNO and its broker operate independently until the link comes back.
====

== Steps

=== 1. Start a Consumer on the Hub

Start a long-running consumer on `messages.NY.test`:

IMPORTANT: Start the consumer *before* simulating the partition so it is subscribed to the topic.

[source,bash,subs="attributes+"]
----
oc -n artemis run consumer-m6 -ti \
  --image=registry.redhat.io/amq7/amq-broker-rhel8:7.12 \
  --rm=true --restart=Never -- /opt/amq/bin/artemis consumer \
  --url=amqp://hub-01-broker-amqp-acceptor-0-svc.artemis.svc.cluster.local:5672 \
  --protocol=AMQP --user={consumer_user} --password={consumer_password} \
  --destination=topic://messages.NY.test --verbose
----

Leave this running in a separate terminal.

=== 2. Simulate Network Partition on sno-edge-01

Policy `policy-block-spoke-01-federation` is created **disabled**. Enabling it enforces a NetworkPolicy on the NY SNO that blocks egress from `spoke-01-broker` (federation to hub-01 drops). Inbound AMQPS from your producer still works.

As cluster-admin (facilitator):

[source,bash]
----
oc patch policy policy-block-spoke-01-federation -n edge-broker-policies \
  --type merge -p '{"spec":{"disabled":false}}'
----

[source,bash,role=execute]
----
oc get policy policy-block-spoke-01-federation -n edge-broker-policies
----

Wait until the policy is `Compliant` on `sno-edge-01`. The hub consumer should stop receiving new NY messages from the SNO.

=== 3. Produce While Disconnected

Produce to the NY SNO Route. Messages stay on the edge broker until federation resumes.

[source,bash,subs="attributes+"]
----
oc -n artemis run producer-m6 -ti \
  --image=registry.redhat.io/amq7/amq-broker-rhel8:7.12 \
  --rm=true --restart=Never -- /opt/amq/bin/artemis producer \
  --url='amqps://spoke-01-broker-amqps-acceptor-0-svc-rte-artemis.apps.sno-edge-01.{guid}.gcp.redhatworkshops.io:443?sslEnabled=true&transport.trustAll=true&transport.verifyHost=false&useTopologyForLoadBalancing=false' \
  --protocol=AMQP --user=admin --password=admin \
  --message-count=20 --message='queued during SNO partition' \
  --destination=topic://messages.NY.test --verbose
----

=== 4. Restore Connectivity

As cluster-admin, disable the policy (it stops enforcing but does *not* delete the NetworkPolicy). Then delete the leftover NetworkPolicy on the SNO with the Hive admin kubeconfig:

[source,bash]
----
oc patch policy policy-block-spoke-01-federation -n edge-broker-policies \
  --type merge -p '{"spec":{"disabled":true}}'
oc extract secret/$(oc get clusterdeployment sno-edge-01 -n sno-edge-01 -o jsonpath='{.spec.clusterMetadata.adminKubeconfigSecretRef.name}') -n sno-edge-01 --keys=kubeconfig --to=/tmp
oc --kubeconfig /tmp/kubeconfig delete networkpolicy block-spoke-01-federation -n artemis
----

=== 5. Observe Store-and-Forward Flush

Watch the hub consumer terminal. The 20 messages should arrive after `hub-01-connection` restarts on the SNO.

Confirm the named connection is started again:

[source,bash,role=execute,subs="attributes+"]
----
curl -sS -u admin:admin \
  'http://spoke-01-broker-wconsj-0-svc-rte-artemis.apps.sno-edge-01.{guid}.gcp.redhatworkshops.io/console/jolokia/exec/org.apache.activemq.artemis:broker=%22amq-broker%22/listBrokerConnections'
----

=== 6. Clean Up

[source,bash]
----
oc delete pod consumer-m6 producer-m6 -n artemis --force 2>/dev/null
----
